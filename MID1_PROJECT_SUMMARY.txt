1. PROJECT IDENTITY & OBJECTIVE
--------------------------------------------------------------------------------
1.1 Project Identity:
    * Official Title : DriftOps (Inline Repair & Verification Gate for dbt-core Pipelines)
    * Project ID     : F26-176-DriftOps
    * Primary Stacks : Python 3.10 / 3.11, sqlglot, dbt-core / dbt-postgres,
                       Docker Engine SDK, PostgreSQL 15, Pydantic v2 Settings, pytest.

1.2 Core Problem Statement:
    In enterprise data platforms and modern analytics stacks, upstream operational
    databases frequently undergo schema modifications—such as column renames, type
    widening/narrowing, additions, and deletions. When these operational migrations
    occur without coordinated updates to downstream analytics repositories, dbt
    compilation or execution jobs break catastrophically in production.
    Traditional recovery relies on human alert triage, tedious SQL debugging, and
    multi-hour manual pull request cycles.

1.3 Core Engineering Objective:
    DriftOps provides a deterministic, AST-based schema drift repair engine and
    verification gate that:
    1. Intercepts schema failure diagnostics and detects semantic drift.
    2. Rewrites affected SQL queries via deterministic Abstract Syntax Tree (AST) transforms.
    3. Spins up isolated, ephemeral PostgreSQL Docker sandbox containers in sub-second cycles.
    4. Executes dbt test suites against candidate patches in the isolated sandbox.
    5. Computes multi-factor risk scores and structural safety gates.
    6. Decides whether to autonomously merge (Tier 1), emit an assist PR (Tier 2),
       or escalate to on-call engineers (Tier 3).

1.4 Target Scope for Mid-1 Evaluation:
    * Complete End-to-End Proof of Concept (PoC) for Failure Class 1: Column Renames
      (e.g., `raw_customers.customer_phone` renamed to `contact_number`).
    * Full integration of the 6-Step repair lifecycle from AST synthesis to tier routing.
    * Strict zero-tolerance hard safety gates (Zero failed dbt tests, C_AST >= 0.80, AST rules pass).
    * Dual-mode operational support: Live Docker execution and deterministic mocked verification.


2. SYSTEM ARCHITECTURE & REPAIR WORKFLOW (STEPS 1 - 6)
--------------------------------------------------------------------------------
DriftOps executes schema repair through six modular, decoupled subsystems:

+------------------------------------------------------------------------------+
|                          DRIFTOPS REPAIR WORKFLOW                            |
+------------------------------------------------------------------------------+
| [Step 1: Scaffolding] -> Strongly typed Pydantic configs & environment loading|
|           |                                                                  |
| [Step 2: Warehouse]   -> PostgreSQL 15 container & Jaffle Shop dbt testbed    |
|           |                                                                  |
| [Step 3: Compiler]    -> sqlglot AST parsing, rewrite, C_AST & safety rules  |
|           |                                                                  |
| [Step 4: Sandbox]     -> Dynamic ephemeral container, view deployment & tests |
|           |                                                                  |
| [Step 5: Safety Gate] -> Hard gates check, DAG blast radius & Tier routing   |
|           |                                                                  |
| [Step 6: Orchestrator]-> Unified runner & visual ANSI-coded CLI demonstrator  |
+------------------------------------------------------------------------------+

--- Step 1: Scaffolding & Configuration Management ---
* Module: `src/config.py`
* Role: Implements `Settings(BaseSettings)` using `pydantic-settings` to guarantee
  strongly-typed, validated runtime environment variables.
* Enforces validation logic:
  - Port numbers clamped between 1 and 65535.
  - Logging levels validated against canonical sets (DEBUG, INFO, WARNING, ERROR, CRITICAL).
  - Risk thresholds validated such that `TIER_2_MAX_RISK >= TIER_1_MAX_RISK`.
  - Cached via `@lru_cache` to provide a thread-safe singleton `get_settings()`.

--- Step 2: Warehouse Simulator & dbt Testbed ---
* Files: `docker-compose.yml`, `testbed/init.sql`, `testbed/dbt_project.yml`, `testbed/profiles.yml`
* Role: Establishes a reproducible warehouse environment mimicking an enterprise
  production database and dbt-core model hierarchy.
* Database: PostgreSQL 15 Alpine (`driftops_postgres`) configured with schemas `raw`
  and `analytics`.
* Testbed DAG Structure:
  - Source Table: `raw.raw_customers` (seeded with 10 synthetic customer rows).
  - Staging View: `analytics.stg_customers` (projects `id AS customer_id`, `customer_phone`, etc.).
  - Downstream Mart: `analytics.customers` (materialized table referencing `stg_customers`).
  - dbt Tests: Enforces constraints (`unique`, `not_null` on `customer_id` and `customer_phone`).

--- Step 3: Compiler Engine (AST Parsing, C_AST, and Rules) ---
* Modules: `src/compiler/ast_parser.py`, `src/compiler/cast_calculator.py`, `src/compiler/rules.py`
* AST Parsing & Rewriting (`ast_parser.py`):
  - Uses `sqlglot` to parse Postgres SQL queries into recursive expression trees.
  - `extract_columns(sql_query)`: Traverses AST to extract unique column identifiers.
  - `repair_column_rename(sql_query, old_col, new_col)`: Identifies occurrences of drifted
    columns. In direct SELECT projections, it rewrites `new_col AS old_col` to preserve
    downstream schema contracts. In WHERE clauses, JOIN conditions, or existing aliases,
    it cleanly substitutes the column identifier.
* Structural Confidence Score (`cast_calculator.py`):
  - Computes composite confidence `C_AST = 0.4 * S_name + 0.4 * T_compat + 0.2 * I_catalog`.
  - `S_name`: Normalized Jaro-Winkler string similarity in [0.0, 1.0].
  - `T_compat`: Evaluates PostgreSQL type compatibility: 1.0 for identical/lossless widening,
    0.5 for explicit coercions (e.g., VARCHAR <-> BIGINT), 0.0 for incompatible types.
  - `I_catalog`: Catalog ordinal invariant check (1.0 if column position matches, 0.0 otherwise).
* Deterministic Rule Validator (`rules.py`):
  - Inspects unpatched vs patched AST trees to prevent hallucinated changes.
  - Rule 1: No new JOIN clauses introduced (`len(patch_joins) <= len(orig_joins)`).
  - Rule 2: No WHERE clause filters injected or altered (`normalize_predicate(orig) == normalize_predicate(patch)`).
  - Rule 3: No new literals, unexpected tables, or mutated GROUP/ORDER/LIMIT clauses.
  - Rule 4: Projection alterations restricted strictly to renamed column aliases or explicit casts.

--- Step 4: Ephemeral Docker Sandbox & Test Harness ---
* Modules: `src/sandbox/container_manager.py`, `src/sandbox/dbt_runner.py`
* Sandbox Lifecycle (`container_manager.py`):
  - Interacts with Docker daemon via Python Docker SDK (`docker.from_env()`).
  - `get_free_port()`: Binds to port 0 on host to allocate an unused ephemeral port.
  - `SandboxContainer.start()`: Boots `postgres:15-alpine` container on dynamic port,
    polling via `psycopg2` readiness probe until database is accepting queries.
  - `seed_schema_and_patch()`: Executes `testbed/init.sql`, creates schemas, drops existing
    views, and deploys the candidate SQL patch as a view in `analytics`.
  - Context Manager (`__enter__`, `__exit__`): Guarantees immediate `stop(timeout=2)` and
    `remove(v=True, force=True)` to prevent orphan containers or memory leaks.
* dbt Test Runner (`dbt_runner.py`):
  - Launches `python -m dbt.cli.main test` targeting the ephemeral container credentials.
  - Captures execution logs and parses `target/run_results.json` (with fallback to CLI log regex).
  - Computes empirical test failure ratio: `F_tests = failed_tests / total_tests`.

--- Step 5: Risk Gates & Tier Decision Engine ---
* Modules: `src/gate/hard_gates.py`, `src/gate/risk_calculator.py`, `src/gate/decision_engine.py`
* Hard Safety Gates (`hard_gates.py`):
  - Zero-tolerance invariants:
    1. `F_tests == 0.0` (all dbt assertions must pass in the shadow sandbox).
    2. `C_AST >= 0.80` (structural confidence must equal or exceed 80% floor).
    3. `ast_rule_valid == True` (no unauthorized syntactic alterations).
  - If ANY condition fails, the candidate patch is immediately blocked and routed to Tier 3.
* Class Overrides (`hard_gates.py`):
  - Prevents autonomous merging for high-consequence drift classes: `column_add`, `column_drop`,
    `nullability_shift`, `type_narrowing`. Forces Tier 2 human review regardless of low risk scores.
* Risk Calculation (`risk_calculator.py`):
  - Computes DAG blast radius: `D_impact = min(1.0, N_downstream / 5.0)`.
  - Calculates composite risk score: `R = 0.5 * D_impact + 0.5 * (1.0 - C_AST)`.
* Decision Engine (`decision_engine.py`):
  - Synthesizes all evaluations into `DecisionResult`:
    * Tier 1 (Auto-Fix) : Hard Gates PASS AND R < 0.20 AND No Class Override.
    * Tier 2 (Assist)   : Hard Gates PASS AND (0.20 <= R < 0.60 OR Class Override Active).
    * Tier 3 (Fallback) : Hard Gates FAIL OR R >= 0.60.

--- Step 6: Pipeline Orchestrator & CLI Demonstrator ---
* Modules: `src/orchestrator/runner.py`, `main.py`
* Pipeline Runner (`runner.py`):
  - Implements `run_drift_repair_pipeline(...)`: connects all steps from broken SQL input
    to final `DecisionResult` output.
  - Accepts `mock_sandbox_result` parameter to support hermetic, lightning-fast unit tests
    in CI environments without requiring a local Docker daemon.
* Visual CLI (`main.py`):
  - Exposes CLI interface with flags `--demo-class1` and `--run-tests`.
  - Generates the standard DriftOps Visual Runlog with ANSI color-coding.

4. MATHEMATICAL FORMULAS & DECISION INVARIANTS
--------------------------------------------------------------------------------
DriftOps replaces heuristic guessing with deterministic, mathematical decision models:

4.1 Structural Confidence Metric (C_AST):
    C_AST = (alpha * S_name) + (beta * T_compat) + (gamma * I_catalog)
    Where:
    - alpha = 0.4  (Weight for name similarity)
    - beta  = 0.4  (Weight for type compatibility)
    - gamma = 0.2  (Weight for catalog ordinal invariant)
    - S_name    in [0.0, 1.0]: Jaro-Winkler string similarity between old and new column names.
    - T_compat  in {0.0, 0.5, 1.0}:
        * 1.0 : Identical types or lossless widening (e.g., INT -> BIGINT, VARCHAR -> TEXT).
        * 0.5 : Valid explicit casts (e.g., VARCHAR -> BIGINT).
        * 0.0 : Incompatible types (e.g., BYTEA -> TIMESTAMP).
    - I_catalog in {0.0, 1.0}: 1.0 if PostgreSQL attribute ordinal position matches, 0.0 otherwise.

4.2 Empirical Test Failure Ratio (F_tests):
    F_tests = (Failed dbt Assertions in Shadow DB) / (Total Executed dbt Assertions)
    Clamped strictly in [0.0, 1.0]. If total tests == 0, F_tests = 0.0.

4.3 DAG Blast-Radius Impact (D_impact):
    D_impact = min(1.0, max(0.0, N_downstream / 5.0))
    Where N_downstream is the number of direct and transitive downstream dbt models.
    Impact saturates at 1.0 for N_downstream >= 5 models.

4.4 Composite Deployment Risk Score (R):
    R = 0.5 * D_impact + 0.5 * (1.0 - C_AST)
    Balances structural uncertainty (1.0 - C_AST) equally against pipeline blast radius (D_impact).

4.5 Hard Safety Gate Preconditions:
    The candidate patch FAILS the hard safety gate if ANY of the following occur:
    - F_tests > 0.0                 (Any test assertion fails in the sandbox)
    - C_AST < HARD_GATE_C_AST_FLOOR (C_AST < 0.80)
    - AST_Rule_Validation == False  (Injected JOINs, modified WHERE clauses, or extra columns)

4.6 Decision Tier Routing Logic:
    +-------------------------------------------------------------------------+
    | Tier 1: Autonomous Auto-Fix                                             |
    | Condition: Hard Gates PASS  AND  R < 0.20  AND  Class Override == False |
    | Action   : Automatically committed and merged to staging branch.         |
    +-------------------------------------------------------------------------+
    | Tier 2: Bounded PR Assist (Human-in-the-Loop)                           |
    | Condition: Hard Gates PASS  AND  (0.20 <= R < 0.60 OR Class Override)   |
    | Action   : Emits suggested patch PR with verified diffs for review.     |
    +-------------------------------------------------------------------------+
    | Tier 3: Hard Block & Manual Fallback                                    |
    | Condition: Hard Gates FAIL  OR  R >= 0.60                               |
    | Action   : Halts pipeline, rejects patch, alerts on-call data engineer. |
    +-------------------------------------------------------------------------+

    pytest -v

    pytest tests/test_sandbox.py tests/test_e2e.py -v

    python main.py --demo-class1
